# Connect an AI client with MCP

The Model Context Protocol (MCP) lets an AI client use rstream to discover a project, manage tunnels or operate WebTTY within the credentials it has been given. Choose the server based on where the client runs and what it needs to access.

| Server | Use it when |
| --- | --- |
| Local, `rstream mcp serve` | The client can start a process on a trusted device. The server can use that device's CLI context, private tunnels and WebTTY identities. |
| Hosted MCP | The client connects over HTTPS from another environment. Use OAuth from a compatible client or a scoped personal access token for Control plane operations. Use a trusted local server for private dialing, local files or authenticated end-to-end WebTTY. |

## Start a local server

[Install the CLI](000-installation.md) and [select a project](002-cli-workflow.md). In your MCP client, register `rstream` as a stdio server with the arguments `mcp serve`. Give it the same configuration and context as the CLI. Run `rstream_runtime_status` from the MCP client to confirm which project it sees.

The hosted endpoint is `https://rstream.io/api/mcp`. Use an OAuth-capable
client or configure a scoped bearer credential. Verify the selected access
with the hosted client's project list. See [hosted MCP authentication](https://rstream.io/docs/integrations/agent-native#authentication)
for supported clients and credential choices.

## Codex setup and remote workflows

Run these commands from the workstation that runs Codex:

```sh
rstream codex setup
rstream codex setup --verify
```

Setup adds or repairs the local rstream entry. If setup reports a conflict, review the existing entry before using `--force` to replace it. Verification starts a fresh MCP process and checks that the local tools are available. Open a new task or reload Codex so it uses that configuration. If the machine still needs login, approve the browser request and prepare the selected project before opening a tunnel or WebTTY session.

### Run and track a remote command

A WebTTY command that fails after it starts can return output already captured. Use the session result to distinguish a process exit from a lost connection.

For a non-interactive command that should continue after the reader disconnects, use `rstream_webtty_session_start` with a published WebSocket or WebTransport server and an explicit execution deadline. Save the returned session ID and use it to inspect, join or stop the existing execution. If the start response is lost, check for the existing execution before retrying. See [WebTTY session operations](webtty/001-session-operations.md) for retention and termination behavior.

### Remote network and MCP bridge

A trusted device can expose a service running on a remote WebTTY host through `rstream_remote_expose`. The host needs the CLI, access to the target service and a project context or explicit connection configuration. This workflow uses a POSIX shell on the remote host. Use the server's advertised execution and filesystem paths when invoking the tools.

To expose a service to rstream clients only, pass `publish: false`. For a
published service, choose token or account authentication before exposing
the listener. For a remote MCP endpoint, provide its MCP path to select
token authentication. Save the exposure ID returned by the tool and use it
with `rstream_remote_expose_stop` when the service is no longer needed.

For a direct WebTTY endpoint protected with authenticated end-to-end encryption, pass the local known-server name to both operations. See [WebTTY identity and trust](webtty/000-configuration.md) for configuring that entry.

## Publish an MCP server from your device

`rstream mcp publish` exposes the local device's MCP tools at `/mcp`. Use a short-lived token scoped to that tunnel and path and share it only with a trusted client. Publication grants access to the complete local tool surface within the available credentials. Configure the client to send the scoped bearer token to `/mcp` and verify
that it can list tools. The same request without a token should be denied.
Stop publication with Ctrl+C. Treat every tool reachable under the server's
local identity as exposed to the authorized client.

WebTTY filesystem operations use the backend configured by the server. WebRTC permits reads only. For either backend, publish only the directory needed for the task and run long-lived WebTTY servers under a dedicated OS account. See [file sharing](008-file-sharing.md) and [WebTTY configuration](webtty/000-configuration.md).
