# MCP

rstream MCP is a connectivity layer for AI agents. It exposes rstream operations as explicit tools while keeping network authority, project scope, device trust, and cleanup semantics in the rstream runtime instead of in prompts or ad hoc shell commands.

There are two related surfaces, not two interchangeable deployments of the same server.

| Surface | Primary role | Deliberate boundary |
| --- | --- | --- |
| `rstream mcp serve` | Trusted workstation and device operations over stdio | Uses local config, project context, private dialing, WebTTY identities, known-server pins, trusted-device material, and local E2E grants |
| Hosted `/api/mcp` | OAuth-scoped Control Plane automation over Streamable HTTP | Has no local shell, private dialer, filesystem sidecar, E2E private keys, or recording decrypt grants |

The local surface is the default when an agent can execute the CLI. Hosted MCP is the fallback for agent runtimes that can call HTTPS but cannot run a device-local process. This is especially important for WebTTY: hosted can inventory servers, manage registered records, run bounded non-E2E commands, read session metadata, export non-E2E recordings, and coordinate control requests; E2E execution and decryption remain local.

## Shared contract

Both surfaces negotiate MCP `2025-11-25`. Shared tools have identical names, titles, and behavior annotations. Input properties and required fields are identical where the operation is genuinely the same; differences are retained only for surface authority, such as local project selectors and E2E identity options versus hosted OAuth project scope.

Every structured tool result is a JSON object and has an object-root `outputSchema`. Collections use semantic keys such as `workspaces`, `projects`, `events`, `servers`, and `sessions` rather than a generic `result` wrapper. WebTTY results identify their source with `surface: "cli"` or `surface: "hosted"`. Registered-server enrollment is consistently returned under `enrollment`.

Tool descriptors include explicit read-only, destructive, idempotent, and open-world hints. These describe behavior for agent planning; they are not authorization controls. Invocation status metadata is short enough for MCP clients to display, and the hosted surface mirrors OAuth security schemes in `_meta` for clients that still read the compatibility location.

Tool execution failures use MCP tool results with `isError: true`. A WebTTY command that fails after starting keeps bounded stdout and stderr, reports a safe `error_kind`, and never discards useful partial output. The hosted collector redacts its delegated connect token before truncation and never returns the authenticated dial URL.

`rstream_webtty_session_start` starts a detached non-interactive command through
the configured Engine. Supply a discovered `rstrm://` URL, `command` and an
explicit integer `execution_seconds` budget (1–86400, within the Engine's
advertised maximum). The target must expose a published WebSocket or WebTransport
endpoint. The result contains the acknowledged `session_id`; save it and use
session get, join or stop instead of repeating the command. The operation closes
stdin and disconnects after acknowledgement, without retaining command output.
An unconfirmed start may already have launched the command and must not be
retried automatically. Local identity, E2E and permission checks remain in force.

`rstream_webtty_session_stop` stops an existing managed execution using its
`session_id`. It joins, acquires control through the Engine's existing
permissions and sends protocol termination without starting another command.
`timeout_seconds` is optional (1–65, default 65). Its structured result retains
`exit_code: null` until native completion is confirmed, including on denied
control, transport loss or cancellation; local errors remain separate. The
operation drains final output without retaining it and releases its participant.

WebTTY commands invoked through local MCP receive an empty standard input. The MCP process input belongs exclusively to the protocol reader; command arguments and environment variables supply command input.

## Local setup

For Codex, follow [setup and verification](#codex-setup-and-remote-workflows) below. The local server uses the selected CLI context and stored workstation identity; runtime preparation repairs that context instead of minting a short-lived handoff token.

The device-only tools cover local tunnel lifecycle, full WebTTY and filesystem operation, remote-local service exposure, and remote MCP discovery/calls. Direct authenticated-E2E WebTTY targets use the local known-server store and identities; workspace-managed sessions use trusted-device material and grants available on that device.

## Hosted transport and authorization

Hosted MCP is served at `/api/mcp` with JSON responses over Streamable HTTP. It validates the `Origin` header when present, rejects a foreign origin with HTTP 403, and requires the negotiated `MCP-Protocol-Version` on post-initialization requests. Valid notifications return HTTP 202 without a body. Malformed JSON and invalid JSON-RPC requests remain distinct protocol errors.

Hosted tools declare their minimum OAuth scopes. Authentication and resource restrictions are enforced server-side; annotations and client-side tool allow-lists are only advisory. E2E targets fail with `requires_local_trusted_mcp`, which means the operation must move to a trusted local surface—not that key material should be uploaded.

## Publication and secrets

`rstream mcp publish` exposes the device surface at `/mcp` through a token-protected tunnel. Use a short-lived token scoped to the exact tunnel and path. Publishing currently exposes the complete local tool set, so it is appropriate only for a trusted consumer with an explicit rstream authorization boundary.

Two hardening items remain intentionally open in [the delegation roadmap](../roadmap/008-mcp-delegation.md): server-enforced tool subsets for published or less-trusted consumers, and out-of-band delivery handles for token and TURN credential material. They must be solved together before treating published MCP as a safe browser-agent delegation surface. Descriptors or client allow-lists do not close either gap.

## Validation

Run from the repository root after [source preparation](001-building-from-source.md).

The Go suite validates framing, JSON-RPC recovery, descriptor completeness, object-shaped structured content, annotations, invocation metadata, and partial WebTTY output:

```bash
go test -modfile=out/ice-patch/go.mod ./...
go test -modfile=out/ice-patch/go.mod -race ./cmd/rstream/cmd
go vet -modfile=out/ice-patch/go.mod ./...
```

Filesystem tools automatically use the server-selected WebDAV or WebRTC backend through the same Go client as `webtty fs`. `rstream_webtty_fs_download` streams to disk; read/text results still materialize their output. WebRTC is read-only: write, mkdir and delete return a clear error, without retrying over WebDAV. Use the advertised `fs_backend` and `fs_mode` inventory fields when planning operations.

## Codex setup and remote workflows


For a Codex workstation, either complete the normal developer-machine path first or register the local MCP server before login and let Codex initiate OAuth.

```bash
rstream codex setup

# Verify the configured MCP process and essential local tool surface.
rstream codex setup --verify
```

`rstream codex setup` writes a Codex MCP server entry that runs `rstream mcp serve`. It validates that the command is executable and that an explicitly inherited `RSTREAM_CONFIG` is a readable file. The local MCP server reuses explicit `RSTREAM_API_URL`, `RSTREAM_CONFIG`, and `RSTREAM_CONTEXT` overrides and can expose OAuth login start/poll tools, runtime preparation for a selected project, runtime status, workspace/project discovery, project creation options, explicit project creation or checkout start, project plan inspection, project logs, usage, TURN usage, short-lived TURN credential minting, stable domain inspection and management, project settings, short-lived delegated token creation, managed local tunnels, WebTTY command execution, WebTTY filesystem sidecar operations, remote network exposure through WebTTY, and remote MCP surface discovery and invocation.

Setup is diagnostic and idempotent:

- `installed` means the entry was added;
- `repaired` means a standard but unusable or incomplete entry was replaced, including a missing executable or unreadable stale `RSTREAM_CONFIG`;
- `already_configured` means the existing entry is semantically equivalent and usable, so `changed=false`;
- `conflict` is an error for an intentional-looking custom command, arguments, timeout, environment, or descendant table. Re-run with `--force` only when replacing that customization is intended.

JSON and YAML output contain at least `changed`, `status`, `config`, `command`, `reload_required`, and safe diagnostics. Paths or values found in stale environment entries are not copied into diagnostics, and token-like environment values are never emitted.

`--force` replaces the complete TOML subtree rooted at `[mcp_servers.rstream]`, including immediate or later `[mcp_servers.rstream.*]` descendants. It does not rewrite other MCP servers, Codex settings, or comments. The edit preserves the existing file permissions and uses an atomic replacement. After an installation, repair or rstream CLI upgrade, open a new Codex task or reload Codex so the configuration and current binary are loaded. Existing tasks keep their already-started MCP child process; neither Homebrew nor code signing can replace code inside that process.

`--verify` starts a fresh configured process with a bounded timeout, performs `initialize` using protocol `2025-11-25`, sends `notifications/initialized`, then calls `tools/list`. It checks for `rstream_runtime_status`, `rstream_context_list`, `rstream_webtty_list`, and `rstream_webtty_exec`. Verification only inspects the local MCP surface: it does not call those tools and therefore needs neither rstream login nor network access. A successful verification proves the installed executable, not the version retained by an older open Codex task; after reloading, run one real read-only tool such as `rstream_runtime_status`.

Use rstream CLI 1.18.1 or later for the full Codex MCP workflow, including runtime preparation, WebTTY filesystem tools, remote exposure, and longer MCP tool timeouts for user-approved login.

MCP does not create a rstream account anonymously. On a clean workstation, login remains the user-approved boundary; if the user does not already have an account, the hosted browser step handles signup or sign-in.

After login, Codex should prepare a project with `rstream_runtime_prepare` before managed local tunnels, WebTTY, remote exposure, or remote MCP calls when no context is ready or the selected context is stale. That tool creates or repairs the local project context with the long-lived developer-machine login token. If several tunnel projects are available and the prompt did not name one, Codex should list the choices and ask instead of inferring from naming conventions alone or adding a preferred example. It must not call `rstream_token_create` for workstation setup; that token endpoint is for short-lived delegated handoff flows.

### Remote network and MCP bridge

When a machine already exposes WebTTY, Codex can use the local MCP server to ask that machine to run `rstream forward` for a service that is local to the remote host. This fills the third side of the remote access model: WebTTY provides command execution, the WebDAV sidecar provides filesystem access when enabled, and `rstream_remote_expose` provides network access to HTTP, TCP, UDP, TLS, DTLS, or QUIC services on the same machine. Agents should read `exec_path`, `fs_path`, and `fs_mode` from WebTTY inventory and pass those values to the matching MCP tools instead of assuming `/` or `/fs`.

The WebDAV sidecar rejects symlinks that resolve outside its configured `--fs-root`, but it is not a sandbox. It is still WebTTY-process filesystem access, so long-lived servers should use a dedicated OS user and the narrowest useful root.

For published exposures, the protocol is an edge-facing tunnel protocol. For private exposures, there is no public edge protocol: HTTP/1.x, HTTP/2, MCP, TCP, and TLS ride over a private bytestream tunnel, while UDP, HTTP/3, DTLS, and QUIC ride over a private datagram tunnel.

For non-MCP published remote services, set `token_auth=true` or `rstream_auth=true` in the MCP call when the endpoint must not be open to the internet. Remote MCP exposures default to token authentication when `mcp_path` is set.

The remote host must have a usable `rstream` binary and context, or the MCP call must pass the required environment with the `env` argument. The persistent remote runner currently expects a POSIX shell on the WebTTY host. The remote expose process is tracked under `$HOME/.rstream/remote-exposes` on the remote host and can be stopped with `rstream_remote_expose_stop`.

Remote expose launches its forwarder with `forward --new-process-group`. This
Unix option gives a deliberately independent forwarder its own process group,
so WebTTY can clean up the launch command's group without stopping that service.
The remote CLI must support this option; an older binary fails the launch
explicitly. It does not change tunnel authorization or publication settings.

For other independently managed Unix forwarders, the same option can be used
with a service manager or a shell that owns the PID, redirects standard streams
and handles shutdown. The option creates neither a background job nor a new
service manager. `rstream run` already owns its tunnel lifecycles and does not
expose this process option through tunnel YAML. Windows does not support this
option; it does not permit escaping a WebTTY Job Object.

When `webtty_url` is a direct authenticated-E2E URL, pass `known_server=<name>`
to `rstream_remote_expose` and `rstream_remote_expose_stop`. The local MCP
server then uses the same known-server store as `rstream webtty exec`: it
verifies the pinned server endpoint identity and loads the associated client
identity without adding a Control plane lookup. For `rstrm://...` targets, MCP
uses live WebTTY inventory first and only reaches the Control plane when
workspace-managed trust requires it.

For local MCP servers running on devices or robots, pass `mcp_path=/mcp` to `rstream_remote_expose`. The created tunnel is labeled with `application-protocol=rstream.mcp`, `rstream.mcp.transport=streamable-http`, and `rstream.mcp.path=<path>`. Codex can then discover the surface with `rstream_remote_mcp_discover`, list its tools with `rstream_remote_mcp_tools`, and call a tool with `rstream_remote_mcp_call`.
